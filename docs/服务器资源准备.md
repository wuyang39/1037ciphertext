# A1-22 服务器资源准备

## 1. 目标

本项目采用“本地开发、按需租用、镜像复用、比赛当天快速部署”的资源策略：

- 日常开发主要在个人电脑完成；
- 需要真实 SGX/TEE 环境时，短期租用阿里云 SGX/vSGX ECS；
- 不长期运行云服务器，降低费用；
- 提前制作可复制的自定义镜像和部署脚本；
- 比赛当天从镜像快速创建节点，完成远程证明后直接演示。

目标不是在比赛当天临时安装软件，而是提前把安装、配置、模型导入和测试流程固化下来。

## 2. 总体工作方式

```text
本地电脑
  ├── 编写代码
  ├── 运行明文模型和 RSS 仿真
  ├── 管理 Git/压缩包/模型包
  └── 通过 SSH 或 VS Code Remote SSH 连接云服务器

阿里云 SGX ECS
  ├── 运行 Gramine-SGX
  ├── 运行 DCAP Quote 和远程证明
  ├── 运行 KAS 与 TEE Worker
  ├── 运行 SecretFlow-SPU 三方节点
  └── 执行最终隐私推理演示
```

个人电脑主要承担开发、编译、调试、配置和客户端运行工作；云服务器承担真实 SGX enclave、远程证明和三方网络联调工作。

## 3. 租用策略

具体机型、地域、备选和购买参数见 [阿里云服务器选型.md](阿里云服务器选型.md)。

### 3.1 第一次租用：环境验证

第一次只需要租用一台支持 SGX/vSGX 的阿里云 ECS，使用数小时完成：

1. 确认实例支持 SGX/vSGX；
2. 安装 Ubuntu、Docker、Gramine-SGX 和 DCAP 组件；
3. 运行最小 Hello Enclave；
4. 生成并验证真实 DCAP Quote；
5. 搭建最小 KAS；
6. 测试 Quote 验证后放行一个测试秘密；
7. 修改 enclave 文件，确认 `MRENCLAVE` 变化并被 KAS 拒绝。

这一步的目标是确认真实云环境可用，不需要接入完整大模型。

### 3.2 本地开发阶段：不持续租用

环境验证完成后，可以释放云服务器，在本地电脑继续开发：

- 编写客户端、KAS、TEE Worker 和部署脚本；
- 运行明文 PyTorch 模型；
- 运行本机三方 RSS 仿真；
- 调试 Transformer 算子、量化、KV cache 和结果重构；
- 编写 mTLS、Ticket、审计和安全负例测试；
- 使用 Git 或本地备份保存所有代码和配置。

本地开发不需要真实 SGX，也不需要 GPU 才能完成大部分软件工作。

### 3.3 第二次租用：远程联调

代码和部署环境基本稳定后，再租用一台或三台 SGX ECS，完成：

- TEE Worker 启动；
- KAS 与远程证明联调；
- enclave 内 mTLS；
- SPU 三方小算子；
- 模型份额加载；
- 私有 Transformer 推理；
- 抓包、镜像篡改、Ticket 重放等安全测试；
- 保存演示截图和性能数据。

如果只是验证单个 TEE 节点，一台即可；如果要验证完整三方 RSS 网络拓扑，建议使用三台 SGX ECS。

### 3.4 比赛当天：短期正式演示

比赛当天创建三台 SGX ECS，执行提前准备好的部署脚本：

```text
创建三台 SGX ECS
    ↓
自动配置安全组和私网 IP
    ↓
启动三个 TEE Worker
    ↓
生成 DCAP Quote
    ↓
KAS 验证 MRENCLAVE、角色和新鲜挑战
    ↓
KAS 放行短期证书、存储密钥和 JobTicket
    ↓
挂载加密模型份额
    ↓
建立三方 enclave mTLS
    ↓
运行健康检查和测试推理
    ↓
启动客户端进行正式演示
```

这样比赛当天只需要等待实例创建、证明和健康检查，不需要现场安装完整软件环境。

## 4. 资源保存方案

### 4.1 自定义镜像

在第一次完整配置好服务器后，创建阿里云 ECS 自定义镜像。镜像可以保存：

- Ubuntu 系统；
- Docker、Python、C++ 和基础依赖；
- Gramine-SGX 运行环境；
- DCAP 客户端和证明工具；
- SecretFlow-SPU、YACL、BRPC；
- TEE Worker 程序；
- KAS 客户端；
- 启动脚本、健康检查脚本和监控工具；
- 不包含秘密的默认配置。

以后可以直接使用这个镜像批量创建三台环境一致的 ECS，避免重复安装。阿里云官方支持从已有实例创建自定义镜像，并使用该镜像创建新的 ECS 实例：

[基于已有实例创建自定义镜像](https://help.aliyun.com/zh/ecs/user-guide/create-a-custom-image-from-an-instance)

[使用自定义镜像创建 ECS 实例](https://help.aliyun.com/zh/ecs/user-guide/create-an-ecs-instance-by-using-a-custom-image)

### 4.2 代码和部署包

代码不应只保存在云服务器中，应在本地和 Git 仓库中保存一个带版本号的交付包：

```text
a122-release/
├── client/
├── kas/
├── tee-worker/
├── mpc/
├── model-package/
│   ├── model_manifest.json
│   ├── precision_plan.json
│   ├── tokenizer/
│   └── encrypted_model_share/
├── deploy/
│   ├── create_instances.sh
│   ├── bootstrap_node.sh
│   ├── configure_security_group.sh
│   └── health_check.sh
├── certificates/
├── benchmark/
├── tests/
└── README.md
```

建议使用明确的版本号，例如：

```text
a122-tee-v1.0.0
```

比赛当天使用经过完整测试的固定版本，不临时修改代码。

### 4.3 模型份额保存

模型权重应在模型导入端完成量化和 RSS 拆分，然后以加密模型份额形式保存：

```text
model_manifest.json
precision_plan.json
tokenizer_hash
encrypted_model_share_P0.bin
encrypted_model_share_P1.bin
encrypted_model_share_P2.bin
```

可以将加密模型份额放入自定义镜像、云存储或单独的数据盘，但必须遵守：

- 镜像中不能保存 `K_disk_i`；
- 不能把 SM2 私钥、KAS 私钥或 TLS 私钥写入镜像；
- 不能把密钥放入 Dockerfile、环境变量或普通配置文件；
- 模型份额只能在 enclave 通过远程证明后由 KAS 放行解封密钥；
- `model_manifest`、模型哈希和量化计划必须进行版本绑定。

这样即使自定义镜像被复制，镜像中也只有无法直接使用的加密材料。

## 5. 比赛当天的一键部署设计

### 5.1 准备的脚本

建议准备以下脚本：

```text
deploy/
├── create_instances.sh            # 创建三台按量付费 SGX ECS
├── configure_security_group.sh    # 配置安全组和端口
├── bootstrap_node.sh              # 初始化节点角色和网络配置
├── install_runtime.sh             # 检查镜像内运行环境
├── start_kas.sh                   # 启动 KAS 和审计服务
├── start_tee_worker.sh            # 启动 P0/P1/P2 Worker
├── health_check.sh                # 检查证明、mTLS、SPU 和模型加载
├── run_demo.sh                    # 启动正式客户端演示
└── release_instances.sh           # 演示结束后释放资源
```

如果使用 Windows 本地电脑，可以再提供一个 PowerShell 入口：

```powershell
.\deploy-demo.ps1
```

这个入口负责调用阿里云 CLI/API 或远程执行部署脚本。

### 5.2 健康检查内容

正式演示前，脚本必须自动检查：

1. 三台实例是否为目标 SGX/vSGX 规格；
2. `/dev/sgx_enclave` 等设备是否可用；
3. Gramine-SGX 是否能启动；
4. DCAP Quote 是否验证通过；
5. `MRENCLAVE` 是否与 release manifest 一致；
6. 三个节点证书是否由 KAS 签发；
7. P0/P1/P2 是否能够通过 enclave mTLS 互联；
8. 加密模型份额是否成功加载；
9. SPU 加法、乘法和 MatMul 是否通过；
10. 客户端是否可以完成一轮私有推理。

健康检查失败时应停止演示并输出明确错误，不应自动降级为无证明运行或明文通信。

## 6. 代码、镜像与密钥的边界

### 6.1 可以提前保存的内容

- 操作系统和软件依赖；
- 经过固定版本的应用代码；
- Docker 镜像；
- Gramine manifest；
- 不含秘密的 KAS 策略；
- 加密后的模型份额；
- tokenizer 和量化配置；
- 自动部署脚本；
- 测试向量和性能脚本；
- 模型与程序哈希。

### 6.2 必须比赛当天重新生成或重新授权的内容

- SGX Quote；
- enclave 临时密钥；
- RA-TLS 临时证书；
- `K_disk_i`；
- 会话密钥；
- `JobTicket`；
- 输入 Prompt 的 RSS 份额；
- KV cache 和临时推理状态。

比赛当天重新生成这些内容是 TEE 安全流程的一部分，不能为了省时间而提前写入镜像。

## 7. 服务器释放与费用控制

### 7.1 推荐做法

按量付费实例使用结束后，应按以下顺序处理：

1. 保存部署日志、Quote、审计摘要和性能报告；
2. 保存最终代码、镜像 ID、模型哈希和配置版本；
3. 创建必要快照或确认自定义镜像可用；
4. 释放 ECS 实例；
5. 检查并释放不再需要的云盘、EIP、快照和公网带宽资源；
6. 在费用中心确认没有持续计费资源。

阿里云官方说明，按量付费实例释放后不再收取实例计算费用，但未随实例释放的云盘、弹性公网 IP、快照等资源可能继续产生费用：

[阿里云按量付费说明](https://help.aliyun.com/zh/ecs/pay-as-you-go-1)

[阿里云 ECS 账单说明](https://help.aliyun.com/zh/ecs/view-billing-details)

### 7.2 节省停机模式

如果短时间内还要重复使用同一台实例，可以考虑节省停机模式。它可以释放部分计算资源，同时保留云盘和实例配置，但云盘、快照等仍可能收费，并且重新启动时不保证原规格资源立即可用。

[阿里云节省停机模式](https://help.aliyun.com/zh/ecs/user-guide/economical-mode)

对于比赛正式演示，建议提前准备自定义镜像，不完全依赖节省停机实例。这样即使原实例无法启动，也可以从镜像重新创建。

## 8. 比赛前准备时间表

### 比赛前一周

- 确认目标地域存在可购买的 SGX/vSGX 规格；
- 用最终镜像创建三台测试实例；
- 完成完整一键部署和端到端推理；
- 测试镜像篡改、错误证书、Ticket 重放和抓包演示；
- 保存正式版本镜像和模型包；
- 记录镜像 ID、模型哈希、release ID 和 KAS 配置。

### 比赛前一天

- 在目标地域重新创建一次三节点环境；
- 验证实例配额、网络、安全组和公网访问；
- 检查自定义镜像状态为可用；
- 将部署包、客户端和展示材料同步到本地多份备份；
- 准备一套不依赖现场编译的客户端和测试数据。

### 比赛当天

```text
创建三台按量付费 SGX ECS
    ↓
执行一键部署脚本
    ↓
完成 Quote 和 KAS 验证
    ↓
完成 mTLS 和 SPU 健康检查
    ↓
运行测试 Prompt
    ↓
展示私有推理、审计记录和安全证据
    ↓
保存日志并释放实例
```

## 9. 应急方案

应准备以下应急材料：

- 自定义镜像 ID；
- Docker 镜像 tar 包；
- Git 仓库或代码压缩包；
- 模型加密份额备份；
- KAS 和部署配置备份；
- 一键部署脚本；
- 本地明文基线演示；
- 已录制的 Quote、KAS 放行和抓包证据。

其中本地明文基线只用于验证模型效果和展示界面，正式的隐私推理演示仍应使用真实 SGX 三节点环境。

## 10. 最终执行原则

整个资源策略可以概括为：

```text
本地开发和保存代码
    → 短期租用一台 SGX 验证环境
    → 制作自定义镜像
    → 本地完成大部分开发
    → 短期租用三台进行联调
    → 固定最终镜像和部署包
    → 比赛当天创建三台实例并一键部署
    → 完成证明、推理和安全演示
    → 演示结束后释放云资源
```

需要牢记：

> 可以提前保存系统环境、程序和加密模型材料，但不能提前保存 Quote、会话密钥、Lease 和 JobTicket。比赛当天重新远程证明并由 KAS 授权，既能实现快速部署，也保持 TEE 安全闭环。
